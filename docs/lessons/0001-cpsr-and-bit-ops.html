CPSR: the CPU's status line — and Go bit ops that make it real

Your README literally says "cpsr (wtf is cpsr?)". This lesson kills that TODO with zero assumed background. It also teaches the Go idiom (&^=, masks, typed constants) you'll use in every instruction you ever implement. One stone, both birds.

0. Ground floor: what a CPU actually is

The GBA contains an ARM7TDMI — a small processor. A CPU is a machine that does one loop, billions of times per second: fetch an instruction from memory, decode it (figure out what it means), execute it (do the thing), repeat. Your entire emulator is just a Go program imitating that loop.

To do its work, the CPU needs somewhere to keep the numbers it's working on. It has 16 of those slots, called registers, named r0 through r15. Each holds one 32-bit number (that's why your Go type is [16]uint32 — an array of sixteen 32-bit unsigned integers, one per register). Registers are the CPU's own private scratch paper — the fastest memory it has, vastly faster than the RAM on a cartridge or even the GBA's on-board RAM.

Imagine a clerk with a 16-slot desk organizer. Every number he's actively working on sits in a slot on the desk. The filing cabinet across the room (RAM) is huge but slow to reach; the desk slots are instant. Two slots have special jobs: slot 14 is a sticky note for "where to return to after an errand" (the Link Register), and slot 15 is a finger pointing at the next instruction on the to-do list (the Program Counter). Emulating the CPU mostly means: faithfully copying this desk, the finger, and the rules for moving them.

Three of the sixteen have fixed roles (cheat sheet): r13 is the stack pointer (where temporary storage starts), r14 is the link register, r15 is the program counter — and reading r15 gives you an address slightly ahead of the current instruction, because the real CPU fetches instructions early to stay fast (a trick called pipelining). You don't need that detail today; just don't panic when you meet it in DawnGBA's code.

1. What is "status", and why does the CPU need it?

Registers r0–r15 hold data. But the CPU also needs to remember facts about what it just did: "was my last result zero? negative? did it overflow?". ARM answers this with one extra 32-bit register that is not part of the r0–r15 array: the CPSR — Current Program Status Register (GBATEK). Each of its 32 bits is a single yes/no switch. You already modelled it in Go: type CPSR uint32. That line was correct — this lesson fills in what it means.

The CPSR is the clerk's status board — a row of little light switches on his desk. After every calculation the CPU flicks switches automatically: "result was Negative" ⬅ on, "result was Zero" ⬅ off, and so on. Later, when game code says "branch if the last compare said equal", the CPU doesn't re-do the math — it just glances at the Zero switch. That's the entire job of the CPSR: cheap memory of recent events, one bit per fact. 32 bits, 32 yes/no answers, all in one number.

2. The bit layout — what each switch means

 31 30 29 28  27   7  6  5  4-0
 ┌──────────────┬───┬────────┬──────┐
 │ N  Z  C  V   │ Q │ I F T  │ mode │
 └──────────────┴───┴────────┴──────┘
   condition      rsv IRQ FIQ THUMB

N, Z, C, V — the condition flags (bits 31–28). After arithmetic the CPU sets these automatically: Negative = bit 31 of the result was 1 (for signed numbers, that means negative); Zero = the result was exactly 0; Carry = the operation produced a carry out (or, for shifts/rotates, the last bit shifted out); oVerflow = the result doesn't fit in a signed 32-bit interpretation. These four bits are read by conditional instructions — ARM's superpower is that every instruction can carry a condition like "only do this if the last result was zero".

Why "negative" = top bit? A 32-bit number can be read two ways: as a plain unsigned number, or as a signed one where the highest bit acts as a minus sign (this is called two's complement). If bit 31 is 1, the signed reading is negative — so N is literally just a copy of that bit. And why does Z exist? Because "compare two numbers" is implemented as "subtract them and see if you got zero" — flicking one switch is cheaper than storing the whole result. Old trick, still how every modern CPU works.

I, F — interrupt masks (bits 7, 6). The game console's hardware (buttons, video, timers) can interrupt the CPU to demand attention. I=1 means "ignore normal interrupts right now"; F=1 means "ignore fast interrupts". Relevant later when you wire up the PPU; today just know what the letters mean.

Interrupts are a doorbell. The game is running along, and ding — the player pressed a button / the screen wants the next frame. The CPU pauses the game, runs a handler, then resumes. The I and F bits are the "do not disturb" sign on the door. Setting I means the doorbell is muted. You'll flip these yourself when you write interrupt handling, much later in the project.

T — THUMB state (bit 5). The ARM7TDMI understands two instruction formats: ARM (every instruction is 32 bits — expressive but fat) and THUMB (16 bits — half the size, fewer options). Games live almost entirely in THUMB because smaller code = cheaper cartridges. The T bit says which format the CPU currently expects. Your InstructionState enum (ARM/THUMB) and this bit must always agree — they're the same fact stored twice.

The CPU is bilingual: it speaks a long-form language (ARM, 32-bit sentences) and a shorthand language (THUMB, 16-bit abbreviations). The T bit is which language it's currently listening in. If it's set but you decode the next instruction as ARM — or vice versa — you read gibberish and the emulator crashes. This is one of the most common emulator bugs, which is why we're making it concrete now.

Mode (bits 4–0). ARM CPUs run in one of several privilege levels: User (normal game code, restricted), IRQ (servicing an interrupt), Supervisor (handling a software interrupt / reset), and others (full table). The low 5 bits of the CPSR encode which. Some modes swap in banked private copies of certain registers — that's a later lesson; today you only need to be able to read the mode.

Think of modes as staff clearance levels at a company. Most of the time the CPU is a regular employee (User mode) with no keys to the server room. When the doorbell rings (interrupt), it temporarily becomes a technician (IRQ mode) with its own private r13/r14 desk slots — so it doesn't scribble over the employee's notes — and demotes itself back when done. You don't implement the switching today. You just learn to look at bits 4–0 and say "ah, we're in IRQ mode right now".

3. Go's bit-manipulation toolkit

You now know the CPSR is "32 yes/no switches in one number". To use it you must flip and read single bits of a uint32. This is 50% of all emulator code, and Go has clean syntax for it. The trick everywhere is the same: build a number with only the bit you care about set (a mask), then combine with a bitwise operator.

const (
    flagN uint32 = 1 << 31   // 1 shifted left 31 places = 0x80000000
    flagZ uint32 = 1 << 30
    flagC uint32 = 1 << 29
    flagV uint32 = 1 << 28
    flagT uint32 = 1 << 5
    modeMask    = 0x1F      // binary 11111 — the low five bits
)

func (c CPSR) Has(f uint32) bool { return c&f != 0 } // is the switch on?
func (c *CPSR) Set(f uint32)     { *c |= f }         // flick switch ON
func (c *CPSR) Clear(f uint32)   { *c &^= f }        // flick switch OFF
func (c CPSR) Mode() uint8       { return uint8(c & modeMask) } // read 5 switches at once
Shifting builds the mask: 1 << 31 means "the number 1, shifted left 31 slots" — i.e. a single 1 in bit position 31 and 0s everywhere else. It's like a strip of 32 light switches with exactly one flipped.

& (AND) tests: AND keeps a bit only where both numbers have it. c & flagZ is zero everywhere except possibly bit 30 — so "is it nonzero?" = "is the Z switch on?".

|= (OR) sets: OR turns a bit on if it's on in either number. OR-ing in the mask leaves all other bits untouched and forces your target bit to 1.

&^= (AND-NOT) clears: unique-to-Go operator; c &^ f = "keep everything in c except the bits in f". It's the surgical-off switch — the opposite of |=.

Masks read fields: a mode like 0x13 lives in the low 5 bits, so c & 0x1F zeroes everything above bit 4 and leaves the mode number intact.

One more Go concept hiding in that code: receivers. func (c CPSR) Has(...) takes a value receiver — Go hands the method a copy, fine because Has only reads. func (c *CPSR) Set(...) takes a pointer receiver — no copy, because Set must change the original. If Set had a value receiver it would flick a switch on a photocopy and your real CPSR would never change — a classic silent Go bug. Rule of thumb: mutate → pointer, read-only → value.

Value receiver = reading a notice pinned to the board (you get a photocopy; writing on it changes nothing). Pointer receiver = being handed the actual pen to write on the board. If your method needs to change the thing, it needs the pen. When you later write cpu.Step() it will need a pointer receiver too — same reasoning.

4. Your win: implement it in pika

Replace type CPSR uint32 with the real thing in internal/cpu/state.go:

  1. Paste the flag constants and the four methods above.
  2. Write func (c CPSR) IsThumb() bool using Has — one line.
  3. Sanity-check in cmd/gba/main.go: create var c cpu.CPSR, call c.Set(flagZ) and c.Set(flagT), then print with fmt.Printf("%032b\\n", c) and c.Mode(). Expected output: a 32-bit string with 1s at positions 30 and 5 only, and mode 0x10… wait, 0x00 actually — the mode bits start at zero until you set them. See what happens when you also c.Set(0x10). That small experiment cements "mode = low 5 bits".

go run ./cmd/gba — watching the exact bits you asked for light up is the dopamine hit. If %032b confuses you, that's "print as binary, pad to 32 digits".
