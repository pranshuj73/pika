Lesson 0003 · ~40 min

Data processing: your first actually-executing instruction

Lessons 1–2 gave you CPU state and the cond gate. Today the CPU does something: you'll decode the data-processing format — the most common instruction family in ARM — and execute MOV through it. This is the moment pika stops being structs and starts being an emulator. Per your preference: no code from me — instructions, layouts, and explanations only. Every line of Go is yours.

1. What "executing an instruction" means in an emulator

Real hardware runs electricity through silicon. An emulator replaces that with three Go steps you perform in a loop forever: fetch (read 4 bytes from the address in PC), decode (slice the 32-bit word into fields), execute (do what the fields say: change registers, flags, or memory), then advance PC. Everything pika will ever be — down to rendering Pokémon FireRed in your terminal — is this loop plus better bookkeeping. Today you build the decode+execute half for one instruction family.

Think of yourself as an actor reading a script written in an utterly rigid language: every sentence is exactly 32 letters, and the meaning of each letter position is fixed by a rulebook. You read a sentence, chop it into positions, look up what each chunk means, act it out, and move to the next sentence. That's it. There is no intelligence anywhere in a CPU — just a very fast, very literal actor. Your job as emulator author is to be exactly as literal, because the game depends on the rulebook being followed to the letter.

2. The instruction families, and why we start here

ARM groups instructions by the two bits at positions 27–26 (GBATEK). Data processing is marked by both bits being 0 — and it's the biggest, most-used family: all the arithmetic, logic, moves, and compares. Roughly: if it computes a value or compares two values, it lives here. The other groups (multiply, load/store, branch…) reuse the same decoding skills on different layouts, so this family teaches you the pattern once and for all.

The two bits at 27–26 are the form's "department" code. 00 = the math department — by far the busiest desk in the office. Learn to process one math form and every other department is the same chore with a different box layout. That's why every emulator tutorial on Earth starts here; it's not tradition, it's leverage.

3. The full layout — every box on the form

From bit 31 down to bit 0, a data-processing instruction is:

 31-28  27 26  25    24-21  20   19-16  15-12  11-0
 ┌──────┬───────┬─────┬──────┬────┬──────┬──────┬──────────┐
 │ cond │ 0  0  │ I   │opcode│ S  │  Rn  │  Rd  │ operand2 │
 └──────┴───────┴─────┴──────┴────┴──────┴──────┴──────────┘

Walk through each box slowly — this table is the lesson:

  • cond (31–28) — lesson 2. Gate the whole instruction through your ConditionPassed before anything else happens.
  • group (27–26) = 00 — the department code. If these bits aren't 00, this isn't a data-processing instruction and your decoder must route elsewhere (later lessons).
  • I (25) — the "immediate" switch. Decides what operand2 is: 1 means "a constant baked into the instruction", 0 means "take a register and optionally shift it". One bit, two completely different readings of the low 12 bits. Miss this bit and everything downstream is garbage.
  • opcode (24–21) — which of the 16 operations (AND, SUB, ADD, MOV… full table in the cheat sheet).
  • S (20) — "should this instruction update the CPSR flags when it finishes?" In assembly this is the S suffix: MOV vs MOVS. Compilers set S when the next instruction will branch on the result.
  • Rn (19–16) — a register number (0–15), i.e. an index into your registers array. The first operand.
  • Rd (15–12) — destination register number. Where the result goes.
  • operand2 (11–0) — the second operand, encoded. See §5.
Read it as a work order: "IF the status board allows it (cond), take register Rn and operand2, run them through machine #opcode, put the answer in register Rd, and update the board if the S checkbox is ticked." The I checkbox decides whether operand2 is a number written directly on the order or a reference to another desk slot. Every box is 3–4 bits, and each is just a small number once you extract it — the shift-then-mask move from lesson 2, seven times over.

4. The critical mindset: Rn and Rd are indices, not values

The most common beginner decoding bug, so read twice: the Rn field does not contain a number to compute with. It contains a register number — usually 0–15, small. The value lives in your registers array at that index. Same for Rd: you don't put the result into the field, you write it into the array slot the field points at. Decode gives you where; the registers array holds what.

The form doesn't say "add 47 and 12". It says "add whatever is in desk slot 4 to 12, and file the answer into desk slot 7". The form only ever holds slot numbers and small attachments. If you catch yourself using an extracted field directly as a value when it's actually a register index — or vice versa — stop and re-ask: "is this box a where or a what?" This one habit prevents an entire category of emulator bugs.

5. operand2, immediate form only (I=1) — the weird rotate trick

When I=1, the low 12 bits split in two: the bottom 8 bits are a value, the top 4 are a rotate amount. The real operand = the 8-bit value rotated right by twice the rotate amount. So rotate=0 (the common case) means: the operand is just the 8-bit value.

Why so strange? Games constantly need constants like 0x00800000 (big, but one bit set). There's no room for 32 bits of constant in the instruction — most of the form is used by the other boxes. ARM's engineers noticed that useful constants are usually small or small with zeros around them. So: store 8 meaningful bits, plus a 4-bit dial for "where to place them" — like storing the digits "8" plus the instruction "shift left six zeros". You get a huge range of round 32-bit constants from 12 bits. The price: awkward constants (like 0x0F0F0F0F) are simply unrepresentable — assemblers must build them in steps. Emulator consequence: implement the rotation exactly, because games rely on every representable value.

Why right rotation by even amounts only? Rotating right by 2r is the same as rotating left by 32−2r — so right-rotation with an even dial covers every even repositioning, and odd positions were deemed not worth a bit. You don't need to agree with the choice; you need to reproduce it faithfully.

6. The 16 opcodes — see the structure

Full table with semantics in the cheat sheet. Structure first, so the table becomes predictable:

  • 0000–0111: compute-and-store. Bitwise (AND, EOR), subtraction family (SUB, RSB — "reverse subtract", operands swapped, for when the constant must come first), addition family (ADD, ADC "add with carry", SBC "subtract with carry", RSC). The carry variants exist so multi-precision math (64-bit numbers from two 32-bit halves) works: add the low halves, then ADC the high halves with the leftover carry.
  • 1000–1011: compare-only. TST, TEQ, CMP, CMN run the exact same math as their store cousins but throw the result away, keeping only the flags. They never write Rd. This is how "compare and branch" works on ARM: CMP sets flags, the next instruction's cond field reads them.
  • 1100–1111: more compute-and-store. ORR, then MOV (no first operand — Rd just gets operand2), BIC ("bit clear": AND with the inverted operand), MVN ("move negative/inverted": Rd gets the bitwise NOT of operand2).

Also note: bit 21 (the low bit of the opcode field) acts as a modifier on the three before it — NOT-ing the operand (AND→BIC, MOV→MVN) or swapping the subtraction direction (SUB→RSB). And V is only touched by arithmetic; pure logical ops leave it alone (a logic result can't "overflow" — no sign involved).

Why does "compare-only" exist when SUB could set the same flags? Because SUB must also store its answer somewhere, and games compare constantly — you'd be forced to sacrifice a register every time. CMP is "do the subtraction, keep only the lesson, throw away the answer". Four dedicated instructions that exist purely to set flags cheaply: that's how central compare-then-branch is to real code.

7. Your objectives (no code — design decisions are yours)

  1. Decode function. Somewhere in internal/cpu, write a function that takes a 32-bit instruction word and returns all seven fields. Decide yourself: a struct for the fields? Named return values? Extract each field with the shift-then-mask move from lesson 2, using the bit layout above.
  2. MOV first (opcode 1101), immediate form only (I=1, rotate=0 for now): if the condition passes, write the operand value into the register at index Rd. That's your first executing instruction.
  3. Wire a manual fetch. In cmd/gba/main.go, hand-assemble a MOV: build a 32-bit word with your chosen cond (use AL), group 00, I=1, opcode for MOV, S=0, Rd=4, operand2 value 42. Feed it through decode → condition → execute. Print your registers afterward.
  4. Prove S. Repeat with S=1 and operand 0 (should set Z) and a value with bit 31 set (should set N). If your flags don't respond, find out why before moving on.
  5. Then add MVN and BIC — they're MOV and AND with one inversion. Confirm MVN of 0 gives 0xFFFFFFFF.

Acceptance: r4 holds 42 after step 3; MOVS with 0 sets Z; MVN of 0 gives all-ones. If step 3's word looks intimidating, remember it's just seven small numbers OR-ed into their boxes — build it field by field, shifting each into place.
